# 政企质量评估数据与指标平台

## 1. 项目目标

本项目用于迁移并整合 `../export` 中已经开发的取数与指标计算脚本，形成一条可重复执行、可追溯、可扩展的数据链路。`../export` 只作为迁移来源和口径参考，不作为项目运行时依赖；已完成迁移的模块必须把所需脚本与非敏感配置纳入本项目。

整体拆分为两个业务模块：

1. **取数模块（collector）**：对接编排、一体化、EOMS、有数平台，按统计周期获取原始数据，完成基础校验后写入数据库。
2. **指标模块（metrics）**：只从数据库读取标准化数据，按照版本化的指标口径计算结果，输出全省、地市、区县等维度的指标及计算明细。

项目长期维护文件和数据库两种数据形态，默认采用 `both` 模式：

1. **文件链路**：各平台取数后保留原始 Excel/CSV/JSON，指标计算结果也可导出 Excel/CSV，方便人工查看、传递和复核。
2. **数据库链路**：同一批原始数据解析后写入数据库，指标结果和明细也写入数据库，用于跨系统关联、增量计算和历史查询。

两种链路共用同一套字段标准化和指标计算规则。不得分别复制一套计算代码，以免文件结果和数据库结果出现口径差异。

`../export` 中现有脚本及历史文件可继续保留作为迁移依据，但项目发布、打包和运行均不得要求该目录存在。连接器迁移完成后，新项目仍会保留文件输出能力，而不是只剩数据库模式。

```text
外部系统
   ↓
collector（唯一取数实现）
   ├──> 原始 Excel/CSV/JSON 文件归档
   └──> storage 入库
             ↓
metrics（唯一指标实现）
   ├──> 数据库指标结果及明细
   └──> Excel/CSV 指标文件
```

本 README 是第一阶段梳理结果，重点回答：

- 需要对接哪些系统；
- 每个系统需要获取哪些数据；
- 单个系统能够计算哪些指标；
- 哪些指标必须联合多个系统的数据计算；
- 后续整合项目建议如何分层和落库。

> 说明：经确认，本项目统一使用“新装报障率”，不使用“新装保障率”。

## 4. 各数据源的初步取数规则

### 4.1 编排：专线开通情况

现有脚本按日期分批下载并按月合并。指标脚本使用的主要字段包括：订单号、订单状态、业务类型、产品名称、订单类型、地市，以及方案设计、资源查询、资源分配、配置激活、开通审核、报结等处理人字段。

首批入库建议保留原始导出全字段，不要只保留当前指标使用字段，以便后续扩展 MPLS-VPN、传输专线、移机、拆机和环节效率类指标。

### 4.2 编排：互联网专线新装单

现有接口条件包括：

- `service_catalog=ProvGCDedicatedLine`；
- `service_type=ProvInternetLine`；
- 按开始、结束日期分批下载；
- 当前指标至少需要产品实例编号、订单创建时间、地市、订单号、客户名称、产品名称。

产品实例编号是与 EOMS 计费号码进行跨系统关联的关键字段。

### 4.3 一体化：售中专线开通工单

当前取数路径为“综调管理 → 装维过程管理 → 工单查询 → 售中工单查询”，接口条件为：

- 时间字段：工单结束时间；
- 数据来源：二编；
- 工单类型：开通；
- 工单状态：全部；
- 业务类型：导出后筛选专线范围。

计算前需要：剔除测试单、限定正式专线业务范围、按工单号去重并保留最终状态。测试单的识别字段和规则尚未在现有 README 中固化，必须补充确认。

### 4.4 EOMS：政企投诉工单

现有取数脚本按日期分页获取投诉列表，并对扩展字段缺失的工单补查详情。计费号码优先使用接口字段及工单文本中识别的 `e55...` 号码；仍为空时，现有重复投诉脚本使用手机号码补位形成客户标识。

正式整合时应同时落库：

- 接口原始字段；
- 标准化计费号码；
- 计费号来源；
- 客户标识；
- 工单号、客服流水号；
- 业务类别完整路径；
- 派单时间、工单状态；
- 所属地市/区县；
- 退单原因、最后处理班组、结单人等口径字段。

重复投诉的“有效工单、分子排除、时间窗口和 Key”应放在指标模块中实现，不应在取数阶段不可逆地删除记录。

其中，EOMS 自身即可提供专线/专网重复投诉率的分子和分母，不需要额外对接在网客户数据：

- 有效工单范围：业务类别包含“专线”或“专网”，客服流水号非空，工单状态为“正常结束”，并剔除主题含“重置鉴权码”的工单；
- 客户标识：优先取计费号码，计费号码为空时使用手机号码补位；两者均为空的记录不进入分母；
- 分母：有效工单范围内的唯一客户标识数；
- 重复投诉 Key：`客户标识 + "|" + 政企市场后的完整业务类别路径`；
- 分子预处理：仅从分子候选中剔除满足特定退单条件的工单，再剔除相同 Key 下间隔不超过 1 小时的重复派单后单；
- 分子：剩余数据中出现至少 2 次的重复投诉 Key 数；
- 公式：`专线/专网重复投诉率 = 重复投诉 Key 数 ÷ 唯一客户标识数`。

### 4.5 有数：企宽新装与投诉清单

现有脚本支持按日期分批导出，企宽新装清单还可按地市拆分。关键关联字段是宽带账号，关键时间字段是新装派单时间和投诉派单时间。

取数模块只负责下载、合并、字段标准化和入库。账号匹配、新装后投诉判断、分子分母聚合放在指标模块完成。

## 5. 建议的项目分层

```text
quality-assessment-pipeline/
├── README.md
├── pyproject.toml           # Python 项目元数据
├── requirements.txt        # 脚本运行依赖
├── config/                  # 数据集、主键、存储模式及后续指标口径配置
├── collector/               # 取数模块
│   ├── orchestration/       # 编排：开通情况、专线新装单
│   ├── integration/         # 一体化：售中开通工单
│   ├── eoms/                # EOMS：政企投诉工单
│   └── youshu/              # 有数：企宽新装、企宽投诉
├── storage/                 # 数据库连接、批次审计与幂等写入
├── metrics/                 # 指标模块
│   ├── opening/             # 开通类指标
│   ├── complaint/           # 投诉/重复投诉类指标
│   └── installation/        # 企宽及专线新装报障类指标
├── sql/                     # SQLite DDL、后续视图及数据核查 SQL
├── tests/                   # 取数解析、口径和回归测试
├── tools/                   # 数据检查工具
└── outputs/                 # 临时报表输出，不作为主数据存储
```

模块边界原则：

- `collector` 不计算业务指标，只获取数据并做无损标准化；
- `storage` 保证同一来源、同一业务主键、同一数据版本不会被重复写入；
- `metrics` 不直接调用外部系统，只读取数据库；
- 每次取数和计算都记录批次、统计周期、代码版本、口径版本和数据时间；
- 原始层数据原则上只增不改，修订通过新批次或版本体现。
- 文件输出和数据库输出必须来自同一个取数批次，并共享 `run_id`；
- 指标文件和数据库指标结果必须来自同一次计算，并共享 `metric_run_id`；
- 文件链路可以单独运行，数据库链路也可以单独运行，生产默认两者同时运行。

## 6. 数据库初步设计

建议至少分为四层：

| 层级 | 用途 | 示例表 |
|---|---|---|
| 运行审计层 | 记录取数与计算是否成功、起止时间、条数、错误信息 | `etl_run`, `metric_run` |
| 原始层（raw） | 基本按源系统字段原样保存，并保留当前记录和历史版本 | `raw_source_record`, `raw_source_record_version` |
| 标准层（dwd） | 字段命名、时间、地市、账号/计费号、业务类型标准化 | `dwd_opening_order`, `dwd_install_order`, `dwd_complaint_order` |
| 指标层（ads） | 保存分子、分母、指标值及口径版本 | `ads_metric_result`, `ads_metric_detail` |

建议所有原始表至少包含以下技术字段：

- `source_system`：来源系统；
- `source_record_id`：源记录业务主键；
- `extract_batch_id`：取数批次；
- `source_file`：原始文件名或接口批次；
- `period_start`、`period_end`：请求数据周期；
- `extracted_at`：取数时间；
- `raw_payload` 或 `raw_row_hash`：原始数据追溯及去重依据；
- `created_at`、`updated_at`：入库时间。

指标结果表至少保存：

- 指标编码和名称；
- 统计周期与统计维度（全省/地市/区县等）；
- 分子、分母、指标值；
- 口径版本；
- 数据批次和计算批次；
- 计算时间；
- 可定位到分子、分母明细的关联信息。

### 6.1 各数据集候选主键

以下结论来自现有脚本含义和 `export`/历史目录中的代表性样例。样例唯一不代表源系统永久保证唯一，因此正式建表前仍需向系统或业务负责人确认。

| 数据集 | 建议的源记录主键 | 当前样例检查 | 不适合作为主键但可用于关联的字段 | 需要确认 |
|---|---|---|---|---|
| 编排：专线开通情况 | `订单号` | 23,913 行，非空 23,913，唯一 23,913 | `产品实例编号`、`CRM工单号`、`宽带账号` | 同一订单状态变化后，源系统是覆盖原订单还是产生新订单号 |
| 编排：互联网专线新装单 | `订单号` | 19,576 行，非空 19,576，唯一 19,576 | `产品实例编号`、`CRM工单号` | 一张订单是否始终只对应一个产品实例；拆分/重开场景如何表示 |
| 一体化：售中专线开通工单 | `工单号` | 40,055 行，非空 40,055，唯一 40,055 | `上游工单号`、`计费号/产品实例编号` | 同一工单重派、撤单重录或状态变化时，工单号是否保持不变 |
| EOMS：政企投诉工单 | 优先 `id`，业务备用键为 `工单号` | 5,738 行；`id` 和 `工单号`均全部非空且唯一 | `客服流水号`、`新客服流水号`、`计费号码`、`手机号码` | `id` 是否为全局且永久稳定的数据库 ID；不同环境或历史迁移后是否会变化 |
| 有数：企宽新装清单 | `工单id` | 杭州样例 51,883 行，全部非空且唯一 | `宽带账号` | `工单id` 是否全省唯一，还是只在地市/日期/报表范围内唯一 |
| 有数：企宽投诉清单 | `工单号` | 32,906 行，全部非空且唯一 | `客服流水号`、`宽带账号` | 工单号是否全局唯一；工单更新后是否仍使用同一工单号 |

当前样例还说明：

- 编排开通情况中的 `产品实例编号`有 2,845 条重复行，不能作为订单记录主键；
- 一体化中的 `计费号/产品实例编号`有大量空值和重复值，不能作为记录主键；
- EOMS 的 `客服流水号`存在空值及重复值，不能作为投诉工单主键；
- 有数企宽新装和投诉数据中的 `宽带账号`均存在重复，这是正常的一账号多工单关系；
- 上述账号、计费号、产品实例编号主要用于跨表匹配和指标计算，不承担唯一标识一行源记录的职责。

### 6.2 数据库内部主键与业务唯一约束

数据库不建议直接把中文业务编号设置成表的物理主键。每张表使用内部生成的 `record_id` 作为物理主键，同时保存源系统主键：

```text
record_id          数据库内部主键
source_record_id   订单号、工单号、工单id 或 EOMS id
extract_batch_id   本次取数/导入批次
```

原始层需要保留同一业务记录在不同取数批次中的快照，因此建议唯一约束为：

```text
(extract_batch_id, source_record_id)
```

标准层表示当前可用于计算的记录，建议唯一约束为：

```text
(source_system, dataset_code, source_record_id)
```

这样，同一工单在两个批次中状态发生变化时，原始层能保留前后两个版本，标准层则更新为最新有效版本。

### 6.3 需要优先向源系统确认的主键问题

1. 编排的 `订单号`是否全局唯一，还是需要与订单类型或来源系统组成联合键。
2. 一体化的 `工单号`在撤单重录后是否复用；若不复用，新旧工单通过哪个字段关联。
3. EOMS 的 `id`是否为稳定的全局 ID，是否比 `工单号`更适合作为接口增量同步游标。
4. 有数的 `工单id`是否跨地市、跨月份全局唯一。
5. 有数企宽投诉的 `工单号`是否会因报表刷新或工单更新而变化。
6. 各系统同一业务记录再次导出时，是否可能修改历史字段；如果会，哪个更新时间字段最可信。

当前开发版本使用 SQLite，数据库默认位于 `data/quality_assessment.db`。生产环境是否继续使用 SQLite，或迁移到 PostgreSQL，需要根据部署位置、并发用户和调度方式确定。

## 7. 当前开发版本使用方法

第一版已经采用 SQLite 实现数据库骨架、数据集主键配置、原始文件归档、幂等导入、变更版本保留和 ETL 批次审计。

存储模式示例见 `config/settings.example.toml`：

- `mode = "file"`：只保留文件，不写数据库；
- `mode = "database"`：写数据库，不额外保留工作文件；
- `mode = "both"`：文件和数据库都保留，作为本项目默认方式。

### 7.4 导入数据

以 EOMS 投诉工单为例：

```bash
python3 storage/import_data.py \
  --database data/quality_assessment.db \
  --dataset eoms_complaint \
  --file "../export/EOMS-投诉工单工具包-精简版/投诉工单/投诉工单_原始数据_20260501-20260731_20260901_191334.xlsx" \
  --period-start 2026-05-01 \
  --period-end 2026-07-31
```

默认会先把源文件按“数据集/归档日期”复制到 `data/raw/`，文件名前附加内容哈希。相同文件再次导入不会重复归档。

支持的数据集编码：

| 数据集编码 | 数据内容 | 主键 |
|---|---|---|
| `orch_opening` | 编排专线开通情况 | 订单号 |
| `orch_install` | 编排互联网专线新装单 | 订单号 |
| `integration_opening` | 一体化售中开通工单 | 工单号 |
| `eoms_complaint` | EOMS 政企投诉工单 | id |
| `youshu_install` | 有数企宽新装清单 | 工单id |
| `youshu_complaint` | 有数企宽投诉清单 | 工单号 |

导入结果中的计数含义：

- `inserted`：该主键首次出现；
- `updated`：主键已存在，但本次内容发生变化，当前表更新并保留新版本；
- `unchanged`：主键和内容均与数据库一致；
- `failed`：缺少主键等原因导致未入库；
- `read`：源文件读取的有效数据行数。

## 8. 从现有脚本迁移时的原则

1. 保留各系统已有的登录、Token 获取、分批下载和文件解析能力。
2. 移除脚本中的固定目录、固定月份和散落的账号配置，统一改为配置或命令行参数。
3. 凭证不得写入仓库、README、日志或数据库业务表，应使用环境变量或专门的密钥管理方式。
4. 下载文件作为审计副本保存，随后解析并幂等入库；不能把 Excel/CSV 继续当成跨模块接口。
5. 将现有计算函数迁移到 `metrics`，并用历史 Excel/CSV 结果建立回归测试。
6. 对跨系统指标统一账号格式、计费号格式、地市名称和时间时区，关联失败记录必须可查询。
7. 每项指标都输出分子明细、分母明细和排除明细，以便业务复核。

## 9. 待业务确认事项

在第二阶段整合代码前，以下事项需要确认并固化：

6. 各指标最终需要的维度和频率：月、季度；全省、地市、区县、产品等。
